## 议题一：Raft 内嵌在 Server 中，还是作为独立服务

### 1.1 背景

当前设计（见架构设计）是**内嵌式**：Raft 库（SOFAJRaft）作为 Maven 依赖打进 Server 进程，每个 Server 本身就是 Raft 节点。

公司内部已有基于 NuRaft（eBay 开源的 C++ Raft 库）的**独立 Raft 服务**：Raft 集群单独部署，业务服务通过客户端读写其中的数据。需要决定本系统是继续内嵌，还是复用这类独立服务。

### 1.2 方案 A：内嵌式（当前设计）

```
        +-------------------- Server 集群（同时也是 Raft 集群）--------------------+
Client->|  Server-0(Leader)  <-->  Server-1(Follower)  <-->  Server-2(Follower)  |
        |  [Raft + FSM + Scheduler + API]  每个节点各自持有日志、快照和内存状态    |
        +----------------------------------+-------------------------------------+
                                           | gRPC
                                         Worker
```

- Server 有状态，使用 StatefulSet + PVC。
- 作业数据存在 FSM 内存中，日志存本地 RocksDB。
- 调度器直接跟着 Raft Leader 走，没有额外的选主逻辑。

### 1.3 方案 B：独立 Raft 服务

```
Client -> Server（无状态，多副本） --KV/锁/watch--> 独立 Raft 服务（NuRaft，3 或 5 节点）
                  |  gRPC
                Worker
```

- Server 无状态（Deployment），作业与任务数据都保存在 Raft 服务提供的 KV 中。
- 调度器是否运行，要靠在 Raft 服务上抢**分布式锁 / 租约**来决定，哪个 Server 抢到谁就是调度 Leader。
- 通过 watch 或轮询感知数据变化。

**副本数说明：**

- **Server 层（无状态）**：不参与 Raft 投票，副本数与一致性无关，2 个即可（挂一个仍可服务，滚动升级不中断）。调度 Leader 由抢锁/租约产生，不是多数派投票：一个为调度 Leader，另一个为热备，Leader 挂掉后租约过期，热备接管。若希望升级期间还能容忍一次意外故障，可用 3 个，这是成本问题而非正确性问题。
- **Raft 服务层**：必须 3 或 5 个节点（3 节点容忍 1 个故障，5 节点容忍 2 个）。2 节点的多数派为 2，挂一个即不可用，容错不优于 1 节点；也应避免偶数节点。
- **注意事项**：
  - 锁/租约必须带 TTL 和 fencing token（单调递增版本号），下游写入校验 token，防止"假死"的旧 Leader 恢复后造成双调度。
  - 租约时长需大于正常抖动（一般几秒到十几秒），在切换速度与误切换之间权衡。
  - Server 的多个副本需配置反亲和（anti-affinity），避免落在同一节点或可用区。
- 租约选主与双 Leader 防护的细节见 1.3.1。

#### 1.3.1 调度 Leader 选举细节

**机制：租约锁，不是投票。** Server 之间不通信、不投票，所有协调都通过 Raft 服务里的一个 key 完成：

```
key:   /scheduler/leader
value: {serverId: "server-1", epoch: 17}
TTL:   10s
```

- **抢锁**：每个 Server 周期性执行 `CAS(key, 不存在 → 自己, TTL=10s)`，成功者为调度 Leader。
- **续约**：Leader 每隔 TTL/3（约 3s）续约一次，把 TTL 重置为 10s。
- **热备**：抢锁失败的 Server 只提供 API（读写 KV），不跑调度器，并继续周期性尝试抢锁。
- **接管**：Leader 挂掉后停止续约，TTL 到期，key 被 Raft 服务删除；热备下一次抢锁成功，并把 `epoch` 加 1。

投票发生在 Raft 服务内部，决定“锁的状态是什么”；Server 层只是锁的使用者，所以 Server 数量不影响一致性。

**2 个副本的表现：**

| 场景 | 表现 |
|------|------|
| 1 个挂了 | 另一个接管，调度中断约一个 TTL（约 10s） |
| 滚动升级 | 先升级热备，再升级 Leader（Leader 优雅退出并主动释放锁），中断接近 0 |
| 升级期间又意外挂 1 个 | API 与调度全部不可用，直到 Pod 被重新拉起 |

3 个副本只多出一点冗余：升级时（暂时只剩 2 个）再挂 1 个，仍有 1 个可用。Server 无状态、Pod 拉起快，通常 2 个就够，要求更高再用 3 个。

**主要风险：双 Leader。** Leader 假死后恢复，会出现两个 Server 同时认为自己是 Leader：

```
t0   S1 是 Leader，租约到 t10
t3   S1 发生 Full GC / 网络停顿 15s
t10  租约过期，S2 抢到锁，epoch=18
t18  S1 恢复，仍以为自己是 Leader，继续触发作业  ← 重复调度
```

应对手段（按重要性）：

1. **Fencing token（必须）**：所有调度写入都带上 `epoch`，在 Raft 服务中以事务校验：`IF /scheduler/leader.epoch == 我的epoch THEN 写入`。S1 恢复后用 epoch=17 写入会被拒绝，双调度被挡在存储层。
2. **本地租约检查**：触发前检查距上次续约成功是否超过 TTL 的安全比例，超过则主动放弃，不依赖 GC 后的感知。
3. **续约失败就降级**：续约请求失败或超时，立即停止调度，不等 TTL 到期。
4. **幂等的 Task 创建**：Task ID 由 `jobId + 触发时间` 确定，重复创建返回已存在，作为最后一道防线。

第 1 点依赖 Raft 服务提供 CAS 或事务（对应 1.5 前提 2）；只有简单 KV 时，要把 epoch 内嵌到被写 key 的版本里，设计更繁琐。

**参数取舍：**

| 参数 | 建议 | 取舍 |
|------|------|------|
| TTL | 10~15s | 越短切换越快，但越易被 GC 或网络抖动误切换；越长故障中断越久 |
| 续约间隔 | TTL/3 | 允许连续丢 2 次续约而不丢锁 |
| 抢锁间隔 | 1~2s | 热备抢锁频率，决定接管延迟 |
| 跨 DC | TTL 取 RTT 的 10 倍以上 | 呼应议题二：跨 DC 时要放宽 TTL |

TTL 由 Raft 服务端计时；Server 端做本地检查时使用单调时钟（`System.nanoTime`），不要用墙上时间。

**与内嵌式的对比：**

| | 内嵌式 | 独立服务 + 租约 |
|---|---|---|
| Leader 唯一性 | Raft 任期保证，不存在双 Leader | 靠 TTL + fencing token 额外保证 |
| 切换时间 | 选举超时（1~3s） | TTL（约 10s） |
| 实现复杂度 | 低 | 中（需处理假死、epoch、降级） |

这是方案 B 的主要隐性成本。

### 1.4 对比

| 维度 | A 内嵌式 | B 独立服务 |
|------|----------|------------|
| 部署单元 | 1 套（Server StatefulSet） | 2 套（Raft 服务 + 无状态 Server） |
| Server 是否有状态 | 有，需要 PVC，扩缩容要走 Raft 成员变更 | 无，任意扩缩容、滚动升级最简单 |
| 读性能 | 本地内存读，微秒级 | 每次读多一次网络往返（可在本地加缓存，但要处理一致性） |
| 写路径 | 客户端→Leader→多数派复制 | 客户端→Server→Raft 服务 Leader→多数派复制，多一跳 |
| 调度器选主 | 直接用 Raft Leader，天然唯一 | 靠外部锁与租约，要处理租约过期、GC 停顿、时钟漂移导致的“双主” |
| 触发的原子性 | `FireJob` 在状态机里一次完成（按 `request_id` 去重并生成 Task） | 需要依赖外部服务的事务或 CAS；若只有简单 KV，要自行设计防重复 |
| Raft 的使用深度 | 完整使用：状态机、快照、成员变更、ReadIndex | 被封装在外部接口后面，业务只调用 KV 与锁 |
| 运维 | 只维护一个系统；但 Server 升级要考虑 Raft 成员稳定 | 需要运维 Raft 服务，但可以由平台团队统一维护、多业务共用 |
| 故障域 | Server 挂了，影响调度与数据 | Raft 服务挂了，所有依赖它的业务都停；Server 挂了不影响数据 |
| 技术栈 | 纯 Java | Java 客户端 + C++ NuRaft 服务，排障跨语言 |
| 数据模型约束 | 可自由设计内存结构与索引（任务索引、租约队列等） | 受限于对方提供的接口：KV、范围查询、事务、TTL、watch 是否齐全 |
| 跨 DC 能力 | 自带 Raft 要自己解决：DC 间延迟、选举超时、节点互通，通常没有专线，难度大（见议题二） | 平台服务可能已具备跨 DC 部署与专线/网络保障（**待确认**），业务直接复用 |

### 1.5 方案 B 的前提条件（需要向平台团队确认）

采用 B 之前，必须确认公司的 NuRaft 服务提供：
1. **强一致 KV**：线性一致读写，带版本号（revision）。
2. **CAS / 事务**：用于“按 `request_id` 去重并创建 Task”这类原子操作；没有事务，只能靠单 key 的 CAS 并重新设计数据布局。
3. **TTL / 租约**：用于调度器选主与 Worker 租约。
4. **范围查询或前缀扫描**：用于列出作业与任务。
5. **Watch 或变更通知**：否则 Follower 与 Worker 只能轮询。
6. **Java 客户端**：或稳定的 gRPC / HTTP 接口。
7. **SLA 与容量**：读写 QPS、数据量上限、可用性承诺。调度系统在高峰时写入频繁（每次触发、分派、上报都是写）。

只要其中缺少事务和租约，方案 B 就需要大量额外的设计来补足，会失去它简单的优势。

### 1.6 倾向与理由

**当前倾向：方案 A（内嵌式）。**

1. 本项目的目标就是“用 Raft 实现作业调度系统”。内嵌式能完整体现复制状态机、Leader 调度、快照与成员变更；方案 B 里 Raft 只是被调用的黑盒。
2. 调度的核心需求（同一次触发只产生一个任务、Leader 切换后不重复分派）依赖“触发动作经过日志提交”，内嵌式下是状态机的天然能力，方案 B 要靠外部事务来保证。
3. 读多写少的场景（查询作业、列表）能直接读本地内存。

**什么情况下改选方案 B：**
- 公司要求统一使用平台的共识服务，不允许业务自带 Raft。
- 作业量很小，希望 Server 完全无状态，且平台服务满足 1.5 的全部前提。
- 团队没有运维 StatefulSet 与持久卷的能力。

### 1.7 折中：保留迁移空间

即使选 A，也可以让存储层面向接口编程：`JobStore` 是接口，`RaftServer.apply()` 是唯一的写入入口。这样将来要换成独立服务，只需新增一套 `ExternalKvJobStore` 与基于租约的 Leader 选举实现，Scheduler、Dispatcher、API 层大体不用改。不过这只是为后续留余地，不作为第一版的目标。

### 1.8 待决事项

- [ ] 确认公司 NuRaft 服务的能力清单（见 1.5），评估能否满足需求。
- [ ] 确认公司是否强制使用统一的共识服务。
- [ ] 确认公司 NuRaft 服务是否已支持跨 DC 部署（见 1.9）。
- [ ] 最终选定方案后，更新架构设计第 2、3 节与部署设计。

### 1.9 引出议题二：跨 DC 能力可能是决定性因素

上面的对比偏向内嵌式，但有一个因素可能改变结论：**跨 DC**。

- 自带 Raft 的内嵌式，多数是单 DC（或同城低延迟机房）内部署。跨 DC 要面对 RTT、抖动、选举超时调大、节点地址互通等问题，一般没有专线保障，业界自带 Raft 的系统很少直接做到跨 DC 的强一致写。
- 公司的 NuRaft 平台服务（eBay 开源的 NuRaft，推测内部有专线或网络层支持），**很可能已经提供跨 DC 的服务能力**，这一点目前只是推测，需要向平台团队确认：是否跨 DC 部署、DC 数量与布局、跨 DC 写延迟与 SLA。
- 如果确认平台已提供跨 DC 能力，而业务又需要抗机房故障，方案 B 的天平会明显向独立服务倾斜：用平台现成的跨 DC 能力，比自己搭内嵌式跨 DC 集群成本低得多。
- 如果业务只需要单 DC 内高可用，则 1.6 的倾向（内嵌式）依然成立。

因此，是否需要跨 DC、以及跨 DC 能带来什么，需要在议题二中单独讨论。

## 议题二：跨数据中心（跨 DC）部署

### 2.1 背景

希望在一个数据中心整体故障（断电、网络中断、机房故障）时，调度系统仍能继续工作，且已提交的作业数据不丢。需要讨论 Raft 集群怎么跨 DC 部署。

### 2.2 跨 DC 对 Raft 的影响

1. **提交延迟**：写入需要多数派确认，延迟等于“凑够多数派所需的最慢那次网络往返（RTT）”。同城 DC 的 RTT 通常 1~5ms，跨城 20~50ms 以上，跨国上百毫秒。
2. **选举超时**：必须明显大于 RTT 与抖动，否则会频繁误选举。跨 DC 要放宽（比如 1s 提到 3~5s），代价是故障切换变慢。
3. **多数派位置**：决定了“哪个 DC 挂了集群还能活”。
4. **分区风险**：DC 之间的链路比机房内部更容易中断，被隔离的少数派一侧无法写入。
5. **Raft 本身没有“异步跨地域复制”**：所有 Voter（投票成员）的复制都在提交路径上，除非用 Learner（见 2.3 方案 C）。

### 2.3 方案

#### 方案 A：单个 Raft 集群，3 个 DC 各放节点（推荐的跨 DC 基线）

```
   DC-1              DC-2              DC-3
 [Server-0]        [Server-1]        [Server-2]       3 节点：每 DC 一个
                                                        任一 DC 整体故障，剩下 2 个仍是多数派
```

5 节点变体：`2 + 2 + 1`（DC-1 两个、DC-2 两个、DC-3 一个），任一 DC 故障剩余 3 个仍是多数派，并且同一 DC 内的单节点故障不会触发跨 DC 选举。

- 优点：任一 DC 故障不丢数据、自动切换（RPO=0，RTO 为选举时间）；就是普通的 Raft 集群，不需要额外机制。
- 缺点：每次提交都要至少等一个**其他 DC** 的确认，写延迟约等于 DC 间最近的 RTT。只适合 DC 之间 RTT 较小（经验上 < 10~20ms）的场景，例如同城多机房。
- 部署要点：
  - 需要 **3 个 DC**。仅有 2 个 DC 时无法获得无单点的多数派（见方案 B）。
  - 调大选举超时，建议为 RTT 的 10 倍以上。
  - 启用 PreVote，避免被隔离的节点重连后打断现有 Leader。
  - 把 Leader 固定在主 DC（见 2.4）。

#### 方案 B：只有 2 个 DC

两个 DC 无法同时满足“任一 DC 故障仍可写”和“不脑裂”：
- 3 个节点 `2 + 1`：多数派在 DC-1，DC-1 整体故障集群就不可写；DC-2 故障则不受影响。
- 4 个节点 `2 + 2`：多数派是 3，任何一边故障都没有多数派，**更差**。

可选做法：
1. **仲裁见证节点（Witness）**：在第三个位置（可以是小机房、云上实例）放一个轻量的仅投票节点，实际变成方案 A 的 `1 + 1 + 1`。见证节点不需要运行调度或存数据，只参与投票，但仍需保存日志（SOFAJRaft 暂无专门的“无数据见证”，用一个小规格 Server 节点代替并禁止其被选为 Leader 即可）。
2. **主备 DC + 人工切换**：多数派放在主 DC，备 DC 只放 Learner（见方案 C）。主 DC 故障后由人工执行强制重置成员（`resetPeers`），会丢失尚未复制到备 DC 的数据。

#### 方案 C：主 DC 多数派 + 备 DC Learner（异步灾备）

```
   主 DC（Voter 多数派）                   备 DC
 [Server-0] [Server-1] [Server-2]  ---->  [Learner-3] [Learner-4]
                                        只复制日志，不参与投票和提交
```

- Learner 是只复制不投票的成员，不在提交路径上，不增加主 DC 的写延迟。
- 备 DC 可以提供就近的只读查询（可能略有滞后）。
- 主 DC 整体故障时，由人工将备 DC 的 Learner 提升为 Voter 并重置集群，**RPO > 0**（最近未复制的日志会丢）、**RTO 为人工操作时间**。
- 优点：延迟最低，适合 DC 间距离远的场景。缺点：非自动切换，有数据丢失窗口。

#### 方案 D：每个 DC 一个独立的 Raft 集群（多 Raft 组 / 分片）

```
   DC-1: Raft 集群 A（3 节点）  负责作业分片 1       DC-2: Raft 集群 B（3 节点）  负责作业分片 2
```

- 每个 DC 内部都是低延迟的 Raft 集群，作业按分片（如 `hash(jobId)` 或按业务归属）分配到各 DC 的集群。
- 优点：每个集群的写延迟都是机房内的，可以水平扩展写吞吐。
- 缺点：一个 DC 整体故障时，它负责的分片不可用，除非每个分片再跨 DC 复制（回到方案 A/C）；还要增加分片路由与全局视图的复杂度。适合“作业天然归属于某个 DC”的场景，且每个 DC 也自成一套 Worker。

### 2.4 Leader 位置与 Worker 位置

不管用哪个方案，都要考虑 **Leader 在哪个 DC**，因为：
- 写请求要经过 Leader；Worker 的 gRPC 长连接、心跳与结果上报都是发给 Leader 的。
- 如果 Leader 在 DC-1，DC-2 的 Worker 每次心跳和上报都是一次跨 DC 通信。

处理办法：
1. **Leader 偏好**：给主 DC 的节点设置更高优先级（SOFAJRaft 支持节点优先级和 `transferLeadershipTo`），并在 DC 恢复后通过 `transferLeadershipTo` 把 Leader 转回主 DC。
2. **Worker 带 DC 标签**：任务可以声明 `labels: {dc: dc-2}`，Dispatcher 优先选择同 DC 的 Worker（本来就有标签匹配策略）。
3. **心跳与续约批量化**：已有设计里 Leader 本地聚合心跳，每 N 秒提交一次，跨 DC 的 Worker 租约时长要大于最大的网络抖动（比如 60s 而不是 30s）。
4. **Worker 就近接入**：Worker 先连本 DC 的 Server，由 Server 转发给 Leader（需要增加转发层），或者仍然直连 Leader。第一版先直连。

### 2.5 Kubernetes 上的跨 DC 部署

方案 A 在 K8s 上有两种做法：

| 做法 | 说明 | 难点 |
|------|------|------|
| **拉伸集群（Stretched cluster）**：一个 K8s 集群跨 3 个 DC，用 zone 做拓扑 | 现有 StatefulSet + `topologySpreadConstraints` 按 zone 分散即可，DNS 与 Service 都不用改 | 控制面（etcd）自己也要跨 DC；对 DC 间网络要求高 |
| **每个 DC 一个 K8s 集群** | 三个集群各部署 1~2 个 Server Pod | headless Service 的 DNS 不能跨集群，需要多集群服务发现（如 Cilium ClusterMesh、Submariner、Istio 多集群）或给每个 Pod 配固定的外部地址（LoadBalancer / NodePort）；PVC 不能跨集群 |

- 两种做法下，Raft 的节点地址必须是**稳定且跨 DC 可达**的名字，这是首要要解决的问题。
- StatefulSet 的 `podAntiAffinity` 与 PDB 仍按 DC 做约束：每个 DC 同时只能有一个节点处于维护状态，避免同时丢多数派。
- 存储：每个 DC 使用本地 SSD 或区域内的块存储，Raft 日志的 fsync 延迟必须低。

#### 2.5.1 基础设施层面的跨 DC 手段（平台 NuRaft 可能的形态）

公司的 NuRaft 服务是否具备跨 DC 能力，取决于 infra 提供了什么。**以下是技术上可行的做法，具体是哪一种需向平台团队确认。**

**对 Raft 有用：网络**

| 手段 | 作用 |
|------|------|
| 专线或私有骨干网（DC 间直连） | 降低 RTT 与抖动、丢包少，是跨 DC Raft 最关键的条件 |
| 同城多 DC（几十公里内） | RTT 可压到 1~3ms，多数派提交延迟接近同机房 |
| 带宽与 QoS 保障 | 避免快照传输或其他业务流量挤占 Raft 复制 |
| 稳定的跨 DC 节点寻址（固定 IP、全局 DNS） | 解决节点互通问题（见 2.5） |

**对 Raft 没用甚至有害：跨 DC 存储**

- Raft 自己负责复制，每个节点保存自己的日志副本；再叠加存储层的跨 DC 同步是重复复制。
- 存储层同步复制会拖慢 fsync，使提交路径延迟叠加。
- 多个节点共享同一份底层存储，会破坏多数派的故障独立性。
- 只有“节点数据盘异地备份（快照）”用于灾难恢复才有意义，它不能替代 Raft 复制。

**平台可能的几种真实形态：**

| 形态 | 对应方案 | 说明 |
|------|----------|------|
| 单 Raft 集群跨 3 DC | 方案 A | 依赖专线，RPO=0，自动切换 |
| 单 DC Raft + 跨 DC Learner 或异步复制 | 方案 C | RPO > 0，人工切换 |
| 每 DC 独立集群 + 上层全局复制层 | 方案 D | 本 DC 分片依赖上层复制，一致性语义要看平台 |
| 仅单 DC | 无 | 不具备跨 DC 能力，也很常见 |

如果平台是前三种之一，议题一的方案 B 可以直接继承其容灾能力；是第四种，则跨 DC 需求要自建（方案 A，要求同城低延迟）或放弃。

### 2.6 对比与倾向

| 方案 | 写延迟 | 容忍整 DC 故障 | RPO | RTO | 复杂度 | 适用 |
|------|--------|----------------|-----|-----|--------|------|
| A 3 DC 单集群 | 一个 DC 间 RTT | 是，自动 | 0 | 秒级 | 中 | 同城多机房，DC 间 RTT < 10~20ms |
| B 2 DC + 见证 | 同 A | 是，自动（需见证节点） | 0 | 秒级 | 中 | 只有 2 个机房但能放一个小见证节点 |
| C 主 DC + Learner | 主 DC 内部 | 否，需人工 | > 0 | 分钟到小时 | 低 | 异地灾备，延迟敏感 |
| D 每 DC 独立集群 | 主 DC 内部 | 本 DC 分片不可用 | 取决于分片是否再复制 | — | 高 | 作业按 DC 天然隔离，需要扩展写吞吐 |

**当前倾向：**
- **第一版：单 DC 内 3 节点部署**（跨可用区 / 机架即可，用 zone 反亲和），先把核心功能做稳。
- **需要抗机房故障时：方案 A**（`2 + 2 + 1` 的 5 节点，或同城 3 DC 每 DC 一个节点）。
- **异地灾备：方案 C**，在远端放 Learner，接受 RPO > 0 并通过人工切换。
- 方案 D 只在作业量大到单个 Raft 组写吞吐成为瓶颈时再考虑，不在初期范围。

### 2.7 跨 DC 对任务调度系统的好处

调度系统是“其他业务的依赖”，它一停，所有任务都无法触发和分派，因此对容灾的要求通常高于普通业务。跨 DC 部署（以 2.3 方案 A 或平台提供的跨 DC Raft 服务为前提）能带来：

1. **整 DC 故障时调度不中断**：Raft 多数派在其余 DC，自动选出新 Leader，调度器随 Leader 切换继续分派，RTO 为秒级。
2. **作业数据不丢（RPO=0）**：作业定义、触发进度、任务状态都已经复制到多个 DC，不会因为一个机房丢失而漏触发、重复触发或丢任务记录。
3. **Worker 不必集中在一个 DC**：各 DC 的 Worker 都能接入同一个调度中心，任务可按 DC 标签就近执行（见 2.4），同时某个 DC 的 Worker 全挂，任务能被调度到其他 DC。
4. **全局统一视图**：所有 DC 的作业在一个系统里管理，避免每个 DC 各自一套调度器，减少配置与运维的重复，也便于做跨 DC 的任务编排与迁移。
5. **维护更灵活**：可以按 DC 滚动做网络、机房、K8s 升级维护，每次只下线一个 DC，不用停调度。
6. **满足合规与容灾要求**：许多业务要求“同城双活/异地灾备”，调度平台自己是单 DC 就成为合规短板。

**代价（需要权衡）：**
- 写延迟上升：每次触发、分派、状态上报都要等跨 DC 多数派确认；调度任务通常是秒级以上，对几十毫秒的提交延迟不敏感，所以**调度系统比交易类业务更容易承受跨 DC 代价**。
- 选举超时与租约要放宽，故障切换变慢。
- 链路分区时，少数派一侧的 DC 无法写入，其 Worker 只能继续执行已有任务，无法上报结果（需要 Worker 本地缓存结果、恢复后补报）。

### 2.8 与议题一的关系

- 内嵌式（方案 A）下，上面所有讨论直接适用于 Server 集群，但需要自己解决跨 DC 的网络互通、延迟与运维，没有专线时只适合同城低延迟 DC。
- 独立服务式（方案 B）下，跨 DC 容灾能力取决于**独立 Raft 服务本身的部署**。如果平台已提供跨 DC 能力，业务只需在每个 DC 各放几个无状态 Server 即可获得容灾，调度 Leader 用租约选出，写延迟取决于 Raft 服务的跨 DC 拓扑。因此无论选哪种，跨 DC 的难点都在“谁是 Raft 集群，它怎么放”。
- **决策建议**：先确认业务是否真的需要抗整 DC 故障（2.9 第一项）。需要，且平台已有跨 DC 能力 → 倾向方案 B；需要，但平台没有 → 内嵌式自建 2.3 方案 A（要求同城低延迟）；不需要 → 保持 1.6 的内嵌式单 DC 部署。

- [ ] 确认平台属于 2.5.1 中的哪种形态；整 DC 故障时 RPO/RTO 的承诺，是自动还是人工切换；能否指定副本所在 DC 与 Leader 偏好；是否有跨 DC 容灾演练记录。

## 议题三：能否让多个节点同时调度任务

### 3.1 背景

目前设计（[架构设计 6.3](./01-architecture-design.md)）里只有 Raft Leader 运行 Scheduler / Dispatcher、接受 Worker 连接。跨 DC 部署（议题二方案 A）时，其他 DC 的 Worker 每次心跳、续约、上报都要跨 DC；Leader 所在节点既要处理写入排序，又要做调度计算和维护所有 Worker 连接。

希望：**多个 Server 节点都能调度任务，Worker 可以就近连任意 Server。** 结论见 3.2：可以，做法是把“分派”设计成 Raft 里的带条件命令，不需要多个 Leader。

### 3.2 核心思路：Raft Leader 只负责排序写入，不等于“唯一的调度者”

“只有 Leader 调度”是当前设计的选择，不是 Raft 的要求。Raft 只要求**所有写入经 Leader 排序**；决定“把哪个 Task 分给哪个 Worker”可以由任意节点做，前提是：**分派是一条带条件检查的 Raft 命令（CAS）**。

先说清楚两个前提：
- 每个 Server 的内存里都有一份完整的 Task 表（FSM），所以**每个 Server 都看得到所有 PENDING 的任务**，不只是 Leader。
- 每个 Server 只和**自己连着的 Worker** 通信。比如 S1 连着 W2，S2 连着 W3。

每个 Server 上都有一个 Dispatcher，循环做下面四步（以 S1 为例）：

**第 1 步：在本机“挑”（只读，不写 Raft）**
- 看本机内存里的 `pendingTasks`，挑一个任务，比如 `t-9001`。
- 从**S1 自己连着的 Worker** 里挑一个有空闲容量的，比如 W2。
- 这只是一个“打算”，还没有生效。因为本机内存可能比集群最新状态慢几十毫秒，别的 Server 也许已经把 `t-9001` 分走了，所以此刻并不知道这个打算是否还成立。

**第 2 步：把“打算”提交给 Raft，让集群来裁决**
- S1 提交命令：`AssignTask{task_id=t-9001, worker_id=W2, expect=PENDING, attempt=1}`。
- 字段含义：“我想把 t-9001 分给 W2；我认为它现在是 PENDING，并且是第 1 次尝试。”
- S1 如果不是 Raft Leader，就把命令转发给 Leader。Leader 把它写进日志，复制给多数派，所有节点按日志顺序执行。

**第 3 步：每个节点按日志顺序执行（apply），并做检查**
- 检查条件：`t-9001` 当前真的是 PENDING 吗？`attempt` 还是 1 吗？W2 的 `running` 还没达到 `capacity` 吗？
- **全部满足** → 把 `t-9001` 改成 RUNNING，记录 `worker=W2` 和租约到期时间，`W2.running +1`。命令**成功**。
- **任何一条不满足** → 状态机什么都不改，命令**失败**（例如 `t-9001` 已经被别的命令改成 RUNNING 了）。
- 因为所有节点执行的是同一份日志、同一套检查，各节点得出的结论一致：成功还是失败，全集群只有一个答案。

**第 4 步：根据结果行动**
- 命令成功 → S1 通过**自己和 W2 之间的 gRPC 连接**把任务推给 W2。只有成功的那个 Server 才推送，所以任务不会被推两次。
- 命令失败 → S1 放弃这个“打算”，回到第 1 步重新挑（更新后的内存里，`t-9001` 已不是 PENDING，会挑别的任务）。

**两个 Server 同时抢同一个任务时：**
```
S1：AssignTask{t-9001, W2, expect=PENDING}  ┐ 几乎同时到达 Leader
S2：AssignTask{t-9001, W3, expect=PENDING}  ┘
Leader 把它们排成日志：index=103 是 S1 的，index=104 是 S2 的
执行 index=103：t-9001 是 PENDING → 改成 RUNNING，worker=W2 → 成功，S1 推送给 W2
执行 index=104：t-9001 已经是 RUNNING，不满足 expect=PENDING → 失败，S2 放弃，重新挑别的任务
```
Raft 日志决定了“谁先谁后”，状态机的检查决定了“先到的成功，后到的失败”。这就是 CAS（compare-and-set：条件满足才修改）。

- **互斥靠 FSM，不靠“只有一个调度者”**：两个节点同时想分派 `t-9001`，Raft 日志把两条 `AssignTask` 排成先后，先 apply 的成功，后 apply 的看到已经是 RUNNING 而失败。任务不会被分派两次。
- **读旧数据是安全的**：Follower 本机内存可能落后，只会导致选错而被拒绝重试，不会导致重复分派。
- **Leader 只负责排序**：Leader 故障时，选举期间写入暂停，选出后各节点的调度立即继续；Follower 的 Worker 连接不受影响。

### 3.3 多节点调度的几种形态

#### 形态 A：Worker 连任意 Server，各 Server 调度自己的 Worker（推荐）

```
 DC-1: Server-0 ←gRPC→ W1, W2      DC-2: Server-1 ←gRPC→ W3, W4      DC-3: Server-2 ←gRPC→ W5
   每个 Server 的 Dispatcher 只分派给自己连着的 Worker，AssignTask 提交到 Raft
```

- Worker 就近连本 DC 的 Server，心跳和任务推送都在本地；Server 把 `RenewLease`、`ReportTask` 作为命令提交到 Raft（Follower 转发给 Leader）。
- 各 Server 对 `pendingTasks` 的取用有竞争：多个 Server 同时想拿 `t-9001`。减少冲突的办法：
  - Task 带 `labels`（如 `dc=dc-2`）时只有匹配的 Server 去取；
  - 无标签的任务按 `hash(task_id) % N` 先由一个“首选 Server”取，超过一定时间（如 1s）没被分派，其他 Server 才可以取，降低冲突。
- Server 宕机：它的 Worker 重连别的 Server；已分派给这些 Worker 的任务靠租约（见 6.3）续约或回收。

#### 形态 B：Worker 拉取任务（Pull）

- Worker 主动向任意 Server 发 `ClaimTask`，Server 提交 `AssignTask`（同样是 CAS）。
- 优点：Server 不需要保存 Worker 连接，更无状态；Worker 容量和负载天然由 Worker 自己控制。
- 缺点：任务分派延迟取决于拉取间隔（可用长轮询缓解）；调度策略（标签、最少负载）要在 Server 侧用 Worker 上报的信息近似实现。

#### 形态 C：按 Task 分片，各节点只调度自己负责的分片

- `hash(task_id)` 或 `hash(job_id)` 决定归哪个 Server 调度，不存在冲突；Server 故障时分片归属由 Raft 里的成员表（也是一条命令）重新分配。
- 缺点：分片归属变更有空窗；Worker 的连接与任务分片不一定在同一个节点，需要转发。

### 3.4 对比

| 形态 | 是否多节点同时调度 | 冲突处理 | Worker 通信本地化 | 复杂度 |
|------|------------------|----------|------------------|--------|
| 当前：只有 Leader 调度 | 否 | 无冲突 | 否 | 低 |
| A Worker 连任意 Server，各自调度 | 是 | FSM CAS，先到先得 | 是 | 中 |
| B Worker 拉取 | 是 | FSM CAS | 是 | 中，分派延迟取决于拉取 |
| C 按分片调度 | 是 | 分片避免冲突 | 视情况 | 中到高 |

注意：不管哪种形态，**每次分派仍是一次 Raft 写入**，吞吐仍受 Leader 单点排序限制。多节点调度提高的是“选择 Worker 的计算并行度”和“Worker 通信本地化”，不是日志写入吞吐。如果写入吞吐成为瓶颈，才需要多 Raft 组分片（3.6）。

### 3.5 例子：两个节点同时分派同一个任务

3 个 Server，S1 连着 W2，S2 连着 W3，Task `t-9001` 刚被 `FireJob`（index=102）提交，S1、S2 的内存里都是 PENDING。

```
t0  S1 的 Dispatcher 选 W2，提交 AssignTask(t-9001, W2, attempt=1)  → 转发给 Leader S0
t0  S2 的 Dispatcher 选 W3，提交 AssignTask(t-9001, W3, attempt=1)  → 转发给 Leader S0
t1  S0 把两条命令排序：index=103 是 S1 的，index=104 是 S2 的
t2  各节点 apply index=103：t-9001 PENDING → RUNNING，worker=W2，租约生效 → 成功
t3  各节点 apply index=104：t-9001 已经是 RUNNING → 拒绝
t4  S1 收到成功，通过自己的 gRPC 流把任务推给 W2
    S2 收到拒绝，放弃 W3，继续取下一个 PENDING 任务
```
结果：任务只分给 W2 一次，不需要选“唯一的调度者”。

**S1 在 t2 之后、推送之前宕机**：和例 6 一样，租约到期后由任意节点提交 `ExpireTask`，Task 回到 PENDING 重新分派。

### 3.6 需要补充设计的点

1. **过期回收**：`ExpireTask` 也可以由任意节点提交，FSM 校验“Task 仍是 RUNNING、attempt 一致、租约确实到期”后才生效；时间以 Leader 写入命令的时间为准（FSM 不读本地时钟）。
2. **Worker 的 fencing**：之前“Worker 拒绝更低 term 的 Leader 推送”的依据改为“每次分派的 `(task_id, attempt)`”，Worker 只接受当前 attempt 的任务，上报时 FSM 也校验 attempt。
3. **并发策略**（`ConcurrencyPolicy`）：`FORBID` 要在 `AssignTask`（或 `FireJob`）的 FSM 校验里判断，不能在各节点本地判断。
4. **Worker 容量**：以 FSM 里的 `running` 计数为准，而不是 Dispatcher 内存里的估计。
5. **写入吞吐**：每次分派都是一条日志，规模大时需要批量（把多个 `AssignTask` 合并成一条）或多 Raft 组（议题三之外的扩展，见议题二方案 D）。

### 3.7 对比：原先“每个 DC 一个 Leader”的思路

“每个 DC 一个 Raft Leader”（多 Raft 组分片）可以降低 Leader 的写入压力，并让一个 DC 的选举空窗只影响自己的分片，但复杂度高，而且跟“能不能多个节点调度”是两个问题。**多节点调度不需要多 Leader。** 多 Raft 组只在日志写入吞吐成为瓶颈时才考虑。

### 3.8 倾向

- **第一版：保持只有 Leader 调度（最简单）**，Worker 带 DC 标签、心跳批量化。
- **要多节点调度、让 Worker 就近连接时：形态 A**。核心改动是把 `AssignTask` 做成带条件检查的命令（上面的 CAS），其余设计（日志、FSM、租约、重试）都可以保留。
- 形态 B 适合 Worker 数量非常多、Server 想保持无状态的场景。
