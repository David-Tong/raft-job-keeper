# Raft 共识算法简介

本文介绍 Raft 的基本概念，以及它在 Raft Job Keeper 中是如何被使用的。系统整体设计见 [01-architecture-design.md](./01-architecture-design.md)。

原论文：*In Search of an Understandable Consensus Algorithm*（Diego Ongaro, John Ousterhout）；可视化演示：<https://raft.github.io>。

## 1. Raft 解决什么问题

### 1.1 问题背景：单机会挂，多机会“不一致”

以作业调度为例，如果调度器只跑在一台机器上，这台机器宕机，所有作业就停摆，作业数据也可能丢失。

那就多部署几台。但多台机器带来新问题：它们各自保存一份数据，如何保证**大家看到的是同一份**？

- 用户在机器 A 上把作业 J 改成“禁用”，机器 B 还不知道，仍在触发 J。
- A 和 B 同时认为自己是调度者，同一个作业被触发两次。
- 网络断了，两边各自继续工作，恢复后数据互相矛盾（**脑裂**）。

这类问题的本质是**分布式共识**：多台机器在可能宕机、消息可能延迟或丢失的环境中，对同一件事（谁是领导者、操作的先后顺序、某条数据的值）达成一致的决定。Raft 就是解决共识问题的算法，Paxos 是同类算法，但 Raft 更容易理解和实现。

### 1.2 Raft 的做法：复制状态机

#### 1.2.1 先理解“状态机”

状态机（State Machine），在 Raft 和本系统的代码中常简称 **FSM**（Finite State Machine，有限状态机）。注意它指的是被复制到每个节点上、按日志顺序执行操作的整个“数据加操作”对象，与任务状态流转（PENDING → RUNNING → SUCCEEDED）不是一回事，后者只是 FSM 里管理的一种业务规则。

状态机就是一个“**当前状态 + 一组操作**”的程序：给它一个操作，它按固定规则把状态变成新状态。比如一个只有“计数”的状态机：

```
初始状态: n = 0
操作 add(5)  -> n = 5
操作 add(3)  -> n = 8
操作 sub(2)  -> n = 6
```

本系统的状态机里装的是作业数据：`jobs`、`tasks`、`workers`，操作就是 `CreateJob`、`FireJob`、`AssignTask` 等。

状态机有个重要性质：**确定性**。只要“初始状态相同、操作序列相同（内容和顺序都相同）”，最终状态就一定相同，与运行在哪台机器、什么时候运行无关。

#### 1.2.2 “复制”的含义

既然确定性成立，要让三台机器的数据一致，就不用同步“数据本身”，只要让**三台机器按同样的顺序执行同样的操作**：

```
        操作序列（日志）: [1] CreateJob(J1)  [2] CreateJob(J2)  [3] DisableJob(J1)
                          |                   |                   |
       节点 A 状态机:  依次执行 1,2,3  ->  J1(禁用), J2
       节点 B 状态机:  依次执行 1,2,3  ->  J1(禁用), J2
       节点 C 状态机:  依次执行 1,2,3  ->  J1(禁用), J2
```

- 这串按顺序排列的操作记录叫**日志（log）**，每条有一个递增的编号 `index`。
- 每个节点各自保存一份日志，各自运行一个状态机，这就是**复制状态机**：状态机被复制到了多个节点上。
- 同步“操作”比同步“数据”更省：数据可能很大，而操作通常很小。

#### 1.2.3 难点：怎么让所有节点的日志一模一样

上面的前提是“所有节点的日志顺序完全一致”，难就难在这里：多个客户端同时发请求、节点随时宕机、网络丢包延迟。如果让每个节点自己决定顺序，就会出现：

```
节点 A 收到的顺序: [DisableJob(J1), DeleteJob(J1)]
节点 B 收到的顺序: [DeleteJob(J1), DisableJob(J1)]   <- 顺序不同，结果不同
```

**Raft 要解决的就是这一件事：保证所有节点的日志顺序完全一致，并且已确认的日志永不丢失。** 它的做法是：
1. **选出一个 Leader**，所有写请求都交给 Leader，由它统一决定顺序，其他节点不能自己定顺序。
2. Leader 把操作追加到自己的日志，再**复制**给 Follower。
3. 日志被**多数派**节点保存后，才算“已提交”，此时才能应用到状态机并返回成功。
4. Leader 宕机后，剩下的节点**重新选举**，新 Leader 必定拥有所有已提交的日志，从它接着往下写。

完整流程可以概括为：

```
客户端命令 -> Leader 追加到日志 -> 复制到多数派 -> 已提交 -> 各节点按相同顺序应用 -> 各节点状态机得到相同状态
```

后面第 4 节会详细讲选举和日志复制是怎么做到的。

### 1.3 用一个例子说明

3 个节点 A（Leader）、B、C，用户提交“创建作业 J1”：

1. 请求到达 Leader A，A 把 `CreateJob(J1)` 追加到自己的日志（此时尚未生效）。
2. A 把这条日志同时发给 B 和 C。
3. B 回复成功。此时 A、B 共 2 个节点已持有该日志，达到多数派（3 个里的 2 个），日志**已提交**。
4. A 把命令应用到状态机（J1 真正创建），并向用户返回成功；随后通知 B、C 也提交并应用。C 即使暂时宕机，恢复后也会自动补齐日志。

如果此时 A 宕机：B、C 已有或能得到已提交的日志，它们选举出新 Leader，J1 不会丢。如果在第 3 步之前 A 就宕机了，用户没有收到成功响应，这条日志可能被丢弃，用户重试即可。**“返回成功即不丢”**是 Raft 的核心保证。

### 1.4 Raft 能保证什么、不能保证什么

| 能保证 | 不能保证 |
|--------|----------|
| 已提交的数据不丢失，所有节点顺序一致 | 少数派存活时仍可写（多数派不可用时，集群宁可停写，也不返回错误的数据） |
| 同一时刻不会有两个都能提交的 Leader（无脑裂） | 吞吐量随节点数增加（写入必须经过 Leader 和多数派，节点越多反而越慢） |
| Leader 故障后自动选举恢复，无需人工介入 | 拜占庭容错（节点作恶、篡改消息）；Raft 假设节点只会宕机，不会说谎 |
| 3 节点容忍 1 个故障，5 节点容忍 2 个故障 | 业务层幂等（客户端超时重试可能让同一命令被提交两次，需由业务自己去重） |

### 1.5 为什么调度系统需要它

| 调度系统的需求 | Raft 提供的能力 |
|----------------|-----------------|
| 调度器不能单点故障 | 自动选举，Leader 挂了几秒内有新 Leader 接手 |
| 同一作业不能被两个调度器重复触发 | 同一时刻只有一个 Leader，且其“触发”动作也要经过日志提交 |
| 作业定义和执行状态不能丢 | 多数派提交后才返回成功，数据保存在多个节点 |
| 故障恢复后状态要连续 | 新 Leader 拥有全部已提交日志，可从中恢复调度进度 |

## 2. 三种角色

| 角色 | 说明 |
|------|------|
| **Leader** | 同一任期内最多一个。接收客户端写请求，把命令追加到日志并复制给 Follower。 |
| **Follower** | 被动接收 Leader 的日志与心跳；一段时间收不到心跳就转为 Candidate。 |
| **Candidate** | 发起选举、拉票的临时角色。 |

角色属于**节点在某一时刻的状态**，并非固定身份；所有节点运行相同的程序。

## 3. 核心概念

- **任期（Term）**：单调递增的整数，相当于逻辑时钟。每次选举开启新任期，每个任期内每个节点最多投一票。
- **日志（Log）**：有序的命令序列，每条包含 `index`、`term`、命令内容。
- **多数派（Quorum）**：`N/2 + 1` 个节点。选举和提交都需要多数派同意。
  - 3 个节点：多数派 2，容忍 1 个故障；5 个节点：多数派 3，容忍 2 个故障。
  - 所以集群节点数应取奇数。
- **提交（Commit）**：日志条目被复制到多数派后即视为已提交，永不丢失，之后才能应用到状态机并向客户端返回成功。
- **快照（Snapshot）**：把状态机当前状态存盘，然后截断此前的日志，避免日志无限增长；落后太多的 Follower 可直接从 Leader 拉取快照追赶。

## 4. 三个子问题

### 4.1 领导者选举
1. Follower 在随机的选举超时（如 1~2 秒）内没收到 Leader 心跳，任期 +1，成为 Candidate，给自己投票并向其他节点请求投票。
2. 获得多数派选票即成为 Leader，并立刻发送心跳宣告身份。
3. 投票时要求候选人的日志至少和自己一样新，保证新 Leader 一定包含所有已提交的日志。
4. 随机超时用来避免多个节点同时竞选而反复分票。

### 4.2 日志复制
1. Leader 把命令追加到本地日志，并行发送 `AppendEntries` 给所有 Follower。
2. Follower 校验前一条日志是否匹配，匹配则追加，否则拒绝，Leader 回退后重发，直到两边日志一致。
3. 多数派确认后 Leader 将其标记为已提交，应用到状态机，并通知 Follower 一并提交。

### 4.3 安全性
- **选举安全**：一个任期内最多一个 Leader。
- **Leader 只追加**：Leader 从不覆盖或删除自己的日志。
- **日志匹配**：两个节点中相同 `index` 且相同 `term` 的日志，其之前的内容完全一致。
- **Leader 完整性**：已提交的日志一定出现在之后所有 Leader 的日志中。

## 5. 常见场景

| 场景 | 行为 |
|------|------|
| Leader 宕机 | Follower 超时后选举出新 Leader，期间写请求暂时不可用（通常数秒内恢复）。 |
| Follower 宕机 | 只要多数派还在，集群照常工作；恢复后自动追赶日志。 |
| 网络分区 | 拥有多数派的一侧继续工作；少数派一侧的 Leader 因无法提交而退位，不会出现两个都能提交的“脑裂”。 |
| 旧 Leader 恢复 | 发现更高任期，立即降为 Follower，其未提交的日志会被新 Leader 的日志覆盖。 |
| 成员变更 | 一次只增删一个节点（或使用联合共识），避免新旧配置同时产生两个多数派。 |

## 6. 读请求的一致性

直接读 Leader 本地状态可能读到过期数据（它可能已被分区隔离而不自知）。常用做法：
- **ReadIndex**：Leader 记录当前提交位置，向多数派确认自己仍是 Leader，等状态机应用到该位置后再读。本系统采用此方式。
- **租约读（Lease Read）**：依赖时钟，性能更好但有时钟漂移风险。
- **Follower 读（stale read）**：可能读到旧数据，但分担 Leader 压力。

## 7. Raft 在本系统中的使用

| Raft 概念 | 本系统中的对应 |
|-----------|----------------|
| 节点 | Server（StatefulSet 的 Pod） |
| 命令 / 日志条目 | 作业与任务的变更：`CreateJob`、`FireJob`、`AssignTask` 等（见架构文档“Raft 命令”） |
| 状态机 | FSM：保存 Job / Task / Worker 的内存存储 |
| Leader | 额外负责运行调度器、分派任务、接受 Worker 连接 |
| 快照 | 定期把 Job / Task / Worker 序列化落盘 |
| 实现库 | [SOFAJRaft](https://github.com/sofastack/sofa-jraft)，已实现上述选举、复制、快照、成员变更与 ReadIndex，无需自行实现 |

**使用时必须遵守的约束：**
1. 一切状态变更都先写入 Raft 日志，再由 FSM 应用。
2. FSM 的应用逻辑必须确定性：不读本地时间、不用随机数，时间戳由 Leader 在构造命令时写入。
3. 调度等只应在 Leader 上运行，且当选后要等历史日志应用完毕才开始。
4. 命令需幂等，因为客户端超时重试可能让同一命令被提交两次。
